# ADR-015: monolito modular containerizado con Compose para una PoC productiva single-host

Estado: propuesto. Fecha: 29/10/2026. Responsable: coordinador de arquitectura. Revisión humana:
pendiente. Plan relacionado: `docs/plan-v2-production-poc.md`.

## Contexto

AgroRAG V1 separa FastAPI y Streamlit por HTTP y mantiene dominio/aplicación independientes de
frameworks y proveedores. Sin embargo, el arranque todavía depende de Python/uv en el host, rutas
relativas, `.env`, dos terminales y un catálogo local preparado manualmente. No existe una unidad
de release que fije imagen, configuración, estado, healthchecks y rollback.

La V2 debe poder desplegarse como PoC en un ambiente productivo sin convertir el proyecto en una
plataforma distribuida. El catálogo SQLite es inmutable para el runtime, el caché vive en memoria y
los modelos/proveedores pueden consumir muchos recursos. Esas restricciones favorecen un host y
una réplica antes que microservicios o Kubernetes.

Esta decisión extiende ADR-003/004/006/009/010/013/014. En particular, reemplaza el límite de
“operación sólo local” de ADR-009 por un perfil productivo acotado; no reemplaza los límites de
seguridad, evidencia, proveedores ni evaluación.

## Decisión

Mantener un monolito modular en el código y separar únicamente unidades de despliegue con Docker
Compose:

1. `api`: FastAPI y composición backend. Una réplica, catálogo read-only y clientes externos.
2. `ui`: Streamlit. Sólo HTTP a `api`; no comparte código interno, SQLite ni secretos de proveedor.
3. `gateway`: única entrada publicada en producción, con TLS/routing/headers y límites HTTP. La
   autenticación de usuario se resuelve en el ingress o IdP del ambiente; la reader key queda como
   credencial interna UI→API.
4. `catalogue-admin`: job explícito para descargar, ingerir, publicar snapshot e indexar. Usa la
   misma release de código, perfil `admin` y volumen read-write. No forma parte de startup.
5. `ollama`: perfil opcional de desarrollo. Producción usa por defecto un proveedor gestionado y no
   carga pesos locales salvo una activación separada y verificada.

Se adoptan un `compose.yaml` común, un overlay de desarrollo y un
`compose.production.yaml`. El overlay productivo no monta código fuente y usa imágenes publicadas
por digest o tag inmutable. Las imágenes se construyen con Dockerfile multi-stage, targets finales
API/UI, dependencias mínimas, usuario no root y labels OCI.

El catálogo reside en un volumen versionado: `catalogue-admin` escribe y publica atómicamente;
`api` lo monta read-only. Startup valida `active.json`, versión y configuración y falla cerrado. No
descarga documentos, pesos ni crea índices/namespaces.

Los secretos se suministran como archivos montados por servicio y la configuración soporta
convención `*_FILE`. `.env` se conserva sólo para desarrollo local. Ningún secreto se incorpora a
imagen, Compose versionado, argumentos de build, logs o healthchecks visibles.

Los contenedores usan healthchecks, restart policy, límites de CPU/memoria, filesystem read-only,
`tmpfs` acotado, capabilities eliminadas y `no-new-privileges` donde corresponda. Logs JSON salen
por stdout/stderr y el host/plataforma decide recolección y retención.

La release se identifica con semver, commit y digest. CI construye y prueba una imagen una vez; la
misma referencia se promueve a staging y producción. Rollback significa volver al digest y
manifiesto de catálogo anteriores, previamente respaldados y probados.

## Alcance de “productiva”

La decisión habilita una **PoC productiva single-host**: acceso controlado, persistencia,
observabilidad básica, supply chain y recuperación reproducible. Acepta mantenimiento programado y
posible interrupción breve durante deploy/rollback.

No declara alta disponibilidad, cero downtime, escalado horizontal, multitenancy, DR multi-región
ni cumplimiento regulatorio. Una segunda réplica requeriría externalizar caché/concurrencia,
resolver coordinación del catálogo y revisar costos/modelos; eso exige otro ADR.

## Alternativas consideradas

### Un único contenedor para UI, API y administración

Rechazada. Mezcla ciclos de vida, healthchecks, permisos y secretos; obliga a supervisar procesos y
permite que la UI acceda a estado backend.

### Kubernetes desde V2

Rechazada. Aumenta superficie operativa sin resolver primero imagen, configuración, estado,
secretos y observabilidad. Compose cubre el objetivo single-host y conserva portabilidad.

### Scripts del host y servicios Python sin contenedores

Rechazada. Mantiene drift de dependencias, rutas y procesos; no produce un artefacto promocionable
por digest ni una prueba real de rollback.

### Microservicios por agente, retrieval y catálogo

Rechazada. Los límites actuales son módulos/puertos internos y no justifican red, contratos
distribuidos ni consistencia adicional. Se preserva el monolito modular.

### Incorporar Redis y PostgreSQL ahora

Rechazada para esta V2. Una réplica y catálogo read-only no lo requieren. Se revisará cuando exista
una necesidad demostrada de escalado, escritura concurrente o disponibilidad.

## Consecuencias

### Positivas

- Un artefacto reproducible ejecuta igual en CI, staging y producción.
- UI, API y administración tienen permisos, healthchecks y secretos mínimos.
- El host no instala toolchain Python ni dependencias del proyecto.
- Catálogo, release y rollback tienen identidad explícita.
- Compose mantiene el costo operacional acorde a una PoC.

### Negativas y trade-offs

- Un solo host y una sola API son puntos únicos de falla.
- Compose no ofrece por sí solo rollout sin interrupción, autoscaling ni reconciliación distribuida.
- Separar imágenes/targets y soportar secret files agrega trabajo de build/configuración.
- Modelos locales pueden aumentar mucho tamaño, memoria y tiempo de arranque; no se incluyen en el
  perfil productivo inicial.
- El LRU sigue siendo efímero y por proceso; reiniciar produce miss.

## Verificación y fitness functions

La decisión se considera aplicada sólo con evidencia de estos controles:

1. `docker compose config` válido para base+dev y base+production, sin secretos en claro ni bind
   mounts de código en producción.
2. Build multi-stage reproducible desde `uv.lock`; targets API/UI ejecutan no root y no contienen
   `.env`, `.git`, tests, toolchain o dependencias dev no justificadas.
3. Suite offline, import-linter y E2E Compose aprueban sin proveedores pagos ni pesos descargados.
4. `docker compose up --wait` alcanza health; UI consulta API por DNS interno.
5. Sólo gateway publica puertos en producción; API/UI no son alcanzables directamente desde host.
6. API no puede escribir el volumen del catálogo; el job admin publica una versión sólo después de
   verificarla y repetirlo es idempotente.
7. Secreto centinela ausente de imagen, `docker compose config`, inspect, logs y respuestas.
8. Recrear contenedores conserva catálogo; backup/restore y rollback de imagen+manifiesto funcionan.
9. CI publica digest, commit, SBOM y resultado de escaneo; una excepción de vulnerabilidad requiere
   riesgo, responsable y vencimiento.
10. Un despliegue en host Linux limpio sigue el runbook sin instalar Python/uv.

## Migración y rollback

La migración es incremental: primero configuración y entrypoints, luego imágenes, Compose local,
estado, seguridad, CI y staging. V1 continúa disponible hasta que el E2E Compose y el ensayo de
rollback pasen. No se cambia retrieval, prompts ni contrato HTTP como parte implícita de
containerizar.

Ante fallo, se detiene la promoción, se vuelve al digest anterior y se monta el snapshot de catálogo
anterior. Nunca se elimina el volumen activo para ocultar un problema. Si el nuevo formato de
catálogo deja de ser backward-compatible, se requiere migración versionada y ADR adicional antes
del deploy.

## Condiciones de revisión

Revisar este ADR si se solicita más de una réplica, acceso público anónimo, escritura concurrente,
datos privados, SLO de alta disponibilidad, proveedor local con GPU o migración a un orquestador.
Esos cambios amplían materialmente seguridad, estado y operación.
