# ADR-013: contratos de recuperación antes de activar proveedores semánticos

Estado: contratos, adaptadores y smoke semántico dev aplicados; activación pendiente. Fecha: 23/10/2026.

## Contexto

La primera versión permite explorar el corpus con BM25. RET-01/02/03 requieren comparar modos sobre las mismas evidencias, rechazar índices incompatibles y limitar el contexto. No hay integración real de Pinecone, embeddings ni tokenizer del modelo generador verificada.

## Decisión

Implementar `RetrievalPipeline` en application con puertos de ranking, reranking y conteo de tokens. El adaptador BM25 expone candidatos antes de aplicar diversidad. Los cuatro modos internos son bm25, vector, hybrid y hybrid_rerank; conservan scores separados de BM25/vector/RRF/reranker. RRF usa k=60 y orden determinista por ID en empates. No comparar scores brutos entre proveedores.

Verificar corpus, modelo, revisión y dimensión antes de aceptar un índice. Resolver todo ID en el catálogo activo y volver a filtrar cultivo antes del reranker. Los IDs desconocidos se excluyen; un reranker que inventa u omite candidatos incumple el contrato. Los proveedores deben devolver scores finitos donde mayor es mejor. Una falla de proveedor es un error operativo, nunca una degradación silenciosa a BM25.

Seleccionar fragmentos completos con cap por source_id y conteo del contexto JSON completo, incluidos encabezados y separadores. Un fragmento que excede el presupuesto se omite; se intenta el siguiente. El contador inyectado debe usar el tokenizer exacto del modelo final, sin truncamiento. Este presupuesto cubre evidencia; no reemplaza el presupuesto global de prompts y llamadas. Defaults: 20 candidatos por etapa, 4 fragmentos finales, 2 por fuente y 3000 tokens de evidencia.

## Activación y límites

Este PR no conecta el pipeline nuevo al bootstrap ni modifica el modo público de exploración. El baseline vigente conserva su comportamiento. Los tests usan rankings y tokenizer dobles; no demuestran recuperación semántica, calidad en español ni tokenización de un modelo real. Tampoco hay caché híbrida ni adaptación async/deadline para proveedores todavía. La identidad declarada por un adaptador deberá contrastarse con metadata real al construirlo, no tomarse de variables arbitrarias del usuario.

El corte `feat/pinecone-adapter` implementa E5/Pinecone y CrossEncoder con carga diferida. La
indexación es administrativa, no destructiva, exige un namespace vacío, verifica los IDs remotos y
publica al final un manifiesto con corpus/modelo/revisión/dimensión. Un índice ausente sólo se crea
con `--create-index`; startup y consultas no crean recursos.

Antes de activar hybrid: usar tokenizer real, ejecutar integración aislada y benchmark dev,
propagar errores a API y ejecutar SDK/CPU fuera del event loop con deadline. No se archiva
03-retrieval ni se declara CAT-04 satisfecho.

El corte `feat/03-retrieval-live-eval` ejecutó los cuatro modos sobre 8 qrels de borrador y un
namespace Pinecone versionado. Vector e híbrido mejoraron varias métricas frente a BM25, pero RRF
redujo Recall@5 frente a vector y el reranker alcanzó p95 aproximado de 30,56 s sólo en retrieval.
Las etiquetas siguen `pending_human`; por estas dos puertas la decisión es no activar aún el modo
híbrido en bootstrap/API. Ver `docs/evidence/tdd/03-live-eval.md`.

## Alternativa

Activar ahora un modo híbrido usando dobles o fallback lexical produciría una funcionalidad engañosa. Mantener contratos testeables permite avanzar sin secretos ni llamadas pagas y deja explícita la integración pendiente.
